# 管理员排障任务流

> 目标：管理员从一个具体报障或已发现的体验事件出发，确认影响范围，定位异常分段和责任域，进一步分析异常原因，并给出可执行的下一步。

---

## 一、任务流总览

```text
1. 发起排障
→ 2. 还原问题现场
→ 3. 确认影响范围
→ 4. 定位异常分段与责任域
→ 5. 异常原因分析
```

| 步骤            | 管理员的问题                   | 该步输出                        |
| ------------- | ------------------------ | --------------------------- |
| 1. 发起排障       | 这次要排查谁的问题？               | 排障对象                        |
| 2. 还原问题现场     | 谁在什么时候访问什么，当时发生了什么？      | 对象、应用、时间、报障现象和当时访问记录        |
| 3. 确认影响范围     | 问题还影响了多少对象，主要集中在哪里？      | 单/多应用、异常数/有效数、共同接入特征和事件关联结果 |
| 4. 定位异常分段与责任域 | 问题发生在访问路径的哪些分段，分别应该由谁处理？ | 异常分段及各自的责任域、关键证据、已排除项和处理方向  |
| 5. 异常原因分析     | 各异常分段内部为什么出现问题？          | 各分段的具体原因、作用机制、证据等级、责任域和处理建议 |

---

## 二、步骤1：发起排障

### 2.1 意图

找到一个具体的用户或分支，建立本次排障的起点。

“发起排障”同时覆盖用户报障和管理员主动排查，比“接收报障”更完整。

### 2.2 场景

| 入口场景       | 管理员行为                     | 输出                 |
| ---------- | ------------------------- | ------------------ |
| 已知报障用户     | 按用户名、账号、终端或IP搜索           | 确认排障用户             |
| 已知报障分支     | 按分支名称或设备搜索                | 确认排障分支             |
| 不知道具体受影响用户 | 从已有体验事件的受影响对象中选择一名用户或一个分支 | 确认代表性排障对象，并带入事件上下文 |

### 2.3 边界

- 本步只确定排障对象，不判断对象的问题类型。
- 不提供全量用户/分支状态排名和汇总分析。
- 不以应用作为一级排障入口。

---

## 三、步骤2：还原问题现场

### 3.1 意图

把用户的“慢”或“打不开”转换成一个可分析的访问上下文，避免用当前状态误判历史问题。

### 3.2 管理员任务

| 管理员操作      | 系统展示                     | 输出         |
| ---------- | ------------------------ | ---------- |
| 确认异常时间     | 该对象在时间附近的应用访问记录          | 分析时间窗      |
| 选择报障应用     | 当时实际访问过的应用及其体验状态         | 本次排障应用     |
| 记录用户反馈现象   | 用户反馈的访问慢或无法访问            | 报障现象       |
| 确认平台是否有效还原 | 对象、应用、时间、接入形态、接入POP和访问结果 | 可继续分析的问题现场 |

平台体验状态只使用“正常/差/不可用/数据不足”。“访问慢”是用户反馈现象，不是平台指标。

### 3.3 场景分支

| 现场还原结果          | 下一步                   |
| --------------- | --------------------- |
| 找到报障应用的有效访问记录   | 进入确认影响范围              |
| 该时间窗没有报障应用的访问记录 | 调整应用或时间窗              |
| 有访问记录，但体验数据不足   | 保留“数据不足”，允许继续查看当前访问路径 |

---

## 四、步骤3：确认影响范围

### 4.1 意图

在进入单对象的路径排查前，先确认问题已经影响了多少对象，异常主要具有哪些共同接入特征，避免直接陷入单用户排查。

### 4.2 任务流

```text
对照当前对象的其他应用
→ 统计同应用的异常对象
→ 分析异常对象的共同接入特征
→ 匹配已有体验事件
```

| 管理员要知道的问题        | 系统展示                                     | 输出               |
| ---------------- | ---------------------------------------- | ---------------- |
| 当前对象是单应用还是多应用异常？ | 当前对象在同一时间窗内的各应用体验状态                      | 单应用异常、多应用异常或无法判断 |
| 同一应用还有多少对象异常？    | 同租户、同应用、同时间窗的异常对象数/有效对象数                 | 当前已知影响数量         |
| 异常对象主要集中在哪里？     | 适用的公网出口IP/办公室、分支、城市、运营商、POP、连接器（ZTNA）等分布 | 最集中的1—2个共同接入特征   |
| 是否已有相关体验事件？      | 已有事件的匹配结果                                | 已关联事件或未关联已有事件    |

相同办公室以相同公网出口IP作为分组依据；只有IP已配置站点映射时，才显示办公室名称。相同出口IP只表示共同接入特征，不直接等于办公室网络故障。

### 4.3 结果分支

| 结果                  | 下一步                    |
| ------------------- | ---------------------- |
| 单体：目前只发现当前对象异常      | 查看当前对象的访问路径            |
| 群体：发现其他异常对象，已关联体验事件 | 可查看事件影响信息；仍可继续查看当前对象路径 |
| 群体：发现其他异常对象，未关联事件   | 查看异常对象和分布；继续查看当前对象路径   |

### 4.4 边界

- 本步只回答“影响了谁、影响多大、主要集中在哪里”。
- 不检查POP、连接器、AF或关键链路是否健康。
- 不还原路径，不定位异常分段，不判断根因和责任方。
- 不新建体验事件。

---

## 五、步骤4：定位异常分段与责任域

### 5.1 意图

还原当前对象在异常时间的实际访问路径，找出异常分段，并判断各异常分段应该由哪个责任域处理。

### 5.2 管理员任务

```text
查看当前访问路径
→ 查看各节点和分段的已有质量与对照证据
→ 确认异常分段
→ 判断责任域和下一步
```

| 管理员要回答的问题       | 系统展示                | 输出                   |
| --------------- | ------------------- | -------------------- |
| 当时实际经过了哪些节点和分段？ | 当前用户/分支到目标应用的实际访问路径 | 可检查的完整路径             |
| 异常发生在哪些分段？      | 各分段的直接质量、异常时间和对照证据  | 一个或多个异常分段            |
| 现有证据分别指向哪些责任域？  | 每个异常分段的直接质量和已有解释证据  | 每个异常分段的责任域、关键证据和处理方向 |

### 5.3 用户访问路径场景

| 场景 | 当前访问路径 | 管理员的核心判断 |
| --- | --- | --- |
| 移动SWG访问SaaS | 客户端 → 客户端到POP → POP处理 → POP到SaaS → 应用响应 | 是用户接入、SASE平台、公网路径还是应用响应问题 |
| 移动ZTNA访问内网应用 | 客户端 → 客户端到POP → POP处理 → POP到连接器 → 连接器 → 内网应用 | 是用户接入、SASE平台、连接器路径还是应用问题 |
| 用户通过GA访问内网应用 | 客户端 → 上车POP → 骨干路径 → 下车POP → 代理网关 → 内网应用 | 是第一公里、骨干路径、代理网关还是内网应用问题 |

### 5.4 分支访问路径场景

| 场景 | 当前访问路径 | 管理员的核心判断 |
| --- | --- | --- |
| 分支SWG访问SaaS | AF转发 → AF到POP → POP处理 → POP到SaaS → 应用响应 | 是AF转发、分支出口、SASE平台还是应用方向问题 |
| 分支组网访问总部 | 分支网关 → 组网路径 → 总部网关 → 总部应用 | 是分支侧、组网路径、总部侧还是应用问题；该场景不涉及连接器 |
| 分支通过GA访问总部 | 分支网关 → 上车POP → 骨干路径 → 下车POP → 总部网关 → 总部应用 | 是分支第一公里、骨干加速路径、总部侧还是应用问题 |

### 5.5 多分段异常

同一次访问可以同时发现多个异常分段。每个异常分段都必须由该分段自身的直接质量和证据独立判定。

平台不根据路径顺序推断分段之间存在上下游影响，也不用一个分段的结论解释另一个分段的异常。

多分段情况下，系统按分段分别展示：

- 分段的异常质量。
- 支持该分段异常的关键证据。
- 该分段对应的责任域。
- 该分段的处理方向。

### 5.6 第4步固定输出

| 输出 | 含义 |
| --- | --- |
| 异常分段 | 访问路径中直接质量异常的节点或分段；存在多个时分别列出 |
| 责任域 | 每个异常分段的证据所支持的处理方，如客户办公室网络、运营商、SASE平台或应用方 |
| 关键证据 | 分别支撑各异常分段和责任域判断的已有证据 |
| 已排除项 | 已有数据显示正常、不是本次主要异常的分段 |
| 处理方向 | 管理员下一步应联系谁或执行什么处理 |

---

## 六、步骤5：异常原因分析

### 6.1 意图

基于已定位的异常分段和已有证据，进一步说明各分段内部发生了什么、如何影响当前访问体验，并给出处理建议。存在多个异常分段时，每个分段分别分析和输出。

### 6.2 管理员任务

```text
进入异常分段
→ 查看已有原因证据
→ 移动接入第一公里、分支第一公里或连接器最后一公里链路变差时，系统自动触发专项诊断
→ 其他分段在现有证据不足时按需触发诊断
→ 获得原因说明和处理建议
```

自动触发覆盖三类场景：

| 场景               | 触发条件                       | 管理员看到的过程              | 输出                      |
| ---------------- | -------------------------- | --------------------- | ----------------------- |
| 移动接入第一公里：客户端到POP | 第4步已根据该分段自身的时延、丢包或抖动确认链路变差 | 进入异常分段时，专项诊断已自动开始或已完成 | 本地接入与公网逐跳质量、异常开始位置和路径对比 |
| 第一公里：AF/分支网关到POP | 第4步已根据该分段自身的时延、丢包或抖动确认链路变差 | 进入异常分段时，专项诊断已自动开始或已完成 | 逐跳质量、异常跳点、ASN/运营商和路径对比  |
| 最后一公里：连接器到POP    | 第4步已根据该分段自身的时延、丢包或抖动确认链路变差 | 进入异常分段时，专项诊断已自动开始或已完成 | 逐跳质量、异常跳点、ASN/运营商和路径对比  |

影响人数较多、关联体验事件、应用体验为“差”，以及AF或连接器资源异常，都不能单独触发这两类链路专项诊断。

### 6.3 输出

| 输出 | 含义 |
| --- | --- |
| 原因结论 | 各异常分段内部发生了什么；存在多个异常分段时分别输出 |
| 关键证据 | 支持原因判断的分段证据、对比证据和专项诊断结果 |
| 证据状态 | 已确认、可能原因或证据不足 |
| 责任域 | 应该承接处理的责任方 |
| 处理建议 | 已确认原因对应处理动作；可能原因对应验证动作；证据不足时说明还缺什么数据 |

---

## 七、后续处置闭环

本节发生在五步排障任务完成之后，不属于当前排障界面的固定步骤。

管理员处理已确认的问题后，围绕原报障对象、应用和时间进行复测。

| 复测结果 | 下一步 |
| --- | --- |
| 体验已恢复 | 完成本次排障 |
| 部分恢复 | 返回当前访问路径，重新检查异常分段和当前判断 |
| 未恢复 | 将当前原因降级为待验证项，回到异常分段继续排查 |

---

## 八、能力边界

- 异常原因必须基于已定位的异常分段和可追溯证据生成。
- 证据不足时明确输出数据边界，不生成确定性原因。
- 存在多个异常分段时，按分段分别分析，不推断分段之间的上下游影响。

---

## 九、AI分析输出

AI不独立发起排障或重新诊断，只组织当前排障界面已经展示的报障上下文、影响范围、实际访问路径、分段证据、对比证据和专项诊断结果。当前界面没有的数据不得进入结论。

| 一级内容 | 包含的子项                               |
| ---- | ----------------------------------- |
| 排障结论 | 结论摘要、结论状态、责任域、判断时间                  |
| 影响范围 | 影响对象、影响应用、影响时间、影响分布、事件关联            |
| 问题定位 | 各异常分段、异常表现、关键证据、对比证据、异常原因、责任判断、已排除项 |
| 处置建议 | 处理对象、建议动作、举证材料、验证建议和后续动作            |

四部分分别回答：结论是什么、影响有多大、问题在哪里且依据是什么、下一步交给谁处理。

AI输出遵循以下边界：

- 多个异常分段分别输出原因、证据、责任域和处置建议，不合并成单一根因。
- 证据不足时明确写“证据不足”及缺少的数据，不使用经验补全原因。
- 默认只给验证建议；只有当前界面已有处置后复测数据时，才增加“恢复状态”。
- 不把建议复测写成已经恢复，不把首个异常跳点直接写成故障设备。
